## What is actually blocking

Ranked by *what could invalidate the project*, not by how open the number is.

### 1. Semantic admission — the only true blocker, and it is fully measurable

Source fitting improves how well the analyser models **whatever texture is
present**. That is the whole point on film grain. It is also the risk: nothing
in the architecture distinguishes film grain from compression dither,
animation line-art, sensor noise or ringing, and a better estimator fits all of
them better.

This failure mode has already blocked deployment once. The 2026-07-16 11-title
campaign found FGS collapsed worst-frame quality on all five non-grain 1080p
titles — VMAF min 31--60 against plain's 94--96 — while saving little or
nothing, sometimes producing a *larger* file than plain.

**Every film in the current eight-film gate is grainy film.** Ju-on and Coming
to America are held out for grain *type*, not content *type*. There is zero
coverage of the class that broke it before, on an architecture with a specific
reason to be worse there.

This needs no reviewer. It is an encode-and-measure job with an unambiguous
pass condition, and it is Phase A below.

### 2. Blind playback — cannot be done, so reduce what it must decide

Not resolvable without a reviewer. The correct response is not to skip it but
to shrink it: measure objective proxies for each named perceptual risk so that
when review time does exist, it is spent on what the proxies could not settle.
Phase D.

### 3. Chroma V amplitude — diagnose, do not fit

V plays at `1.087` mean with Taxi `1.182` and The Shining `1.330`. Two
estimators have now failed. A third fitted constant would repeat the mistake
the findings already name. What is missing is *why* V over-delivers, which is a
diagnostic question. Phase B.

### 4. Per-luma bands — same shape, lower stakes

Deer Hunter `0.250--0.375` at `1.158`, Taxi `0.375--0.500` at `0.893`. Local
closure improved band shape and worsened whole-title bias, so the two are
coupled and the coupling is not understood. Phase C.

### Not on the list: speed

`26.9` fps is the *decode* ceiling of the lossless test intermediate, not the
encoder. Measured 2026-08-04: decoding the source alone runs at 26.9 fps, the
full FGS encode at 26.94, plain NVENC at 29.08. The analyser and encoder are
entirely hidden behind forced `--avsw` software decode of a 4K10 ffvhuff file.
Production inputs are hardware-decodable. There is no speed problem to solve;
there is an unmeasured speed, and one run against an NVDEC-decodable input
would measure it.

## Phase A — admission regression on non-grain content

**Question.** Does the source-static architecture damage non-grain content more
than production does?

**Corpus.** Untouched originals from `/tmp/downloads/movies`, never library
copies — four 1080p H.264 SDR titles spanning the class that broke before:

- `Den.Tid.Paa.Aaret.2018` — Nordic WEB-DL, clean digital
- `Tuner 2025` — modern digital BluRay remux
- `Train.to.Busan.2016` — digital BluRay remux
- `Sinister.2012` — BluRay remux, some real grain, the boundary case

**Arms.** Plain (control), production `modelsrc=off`, candidate
`modelsrc=on` + `NVENC_FGS_TEST_SOURCE_STATIC=on`. Same bilateral separator,
same rate.

**Read.** VMAF mean and p1 against the lossless source clip, bytes against
plain, and the emitted grain table's signalled strength — the last one answers
whether the analyser engages at all, which is the actual admission question.

**Pass condition, set before running.** The candidate must not be materially
worse than production on VMAF p1, and must not signal materially more grain on
content that has none. A candidate that engages harder on clean content is a
regression regardless of how good its film-grain modelling is.

## Phase B — why V over-delivers

Not another estimator. Three checks that separate the candidate causes:

1. **Is it the estimate or the delivery?** Compare the analyser's intended V
   target against `chroma_emission_audit.py`'s exact replay of the emitted
   table. Emission is already proven pixel-exact, so a gap here localises the
   error to curve construction — quantisation, point reduction or the shared
   `scaling_shift` with luma.
2. **Is it the mask?** V uses the luma-derived flat/static selection. Measure
   the V grain energy inside luma-selected blocks against V-selected blocks. If
   they differ materially, the population is the bug and the plane-specific
   selector was rejected for the wrong reason.
3. **Is it the base?** V's pre-encode leak may simply be smaller than the
   spatial estimate assumes, in which case the closure over-signals by
   construction — the same error the luma temporal work already fixed for Y and
   never repeated for chroma.

## Phase C — the band/title coupling

Local per-luma closure reduced band MAE 9.4% and drove every title lower.
That trade is a fact about the estimator, not a tuning constant: it means the
bins where strength is measured are not the bins where it is played. Measure
the luma histogram of the *measured* blocks against the histogram of the blocks
where grain is *delivered*. If they differ, curve population is the mechanism
and no per-bin scalar can fix it.

## Phase D — proxies that shrink the eventual review

Each named perceptual risk with an objective stand-in, so review time is spent
only on what these cannot settle:

| risk | proxy | status |
| --- | --- | --- |
| banding from level compensation | CAMBI on grain-disabled bases | **done**, corpus mean -0.004 |
| dark-band lift | mean luma of near-black flat blocks, candidate vs production | not run |
| chroma crawl | temporal autocorrelation of the U/V grain field; real grain decorrelates frame to frame | not run |
| grain pumping | per-frame delivered amplitude variance across a scene | not run |
| coarse/fine scale error | lag-1/lag-2, already the primary metric | done |

None of these replaces watching it. They bound how much watching is needed.

## Order

Phase A first and alone, because it is the only one that can invalidate the
architecture rather than refine it. B, C and D are refinements on a model that
already beats SVT-AV1's, and none of them matters if the analyser cannot be
trusted to leave clean content alone.
